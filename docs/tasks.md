## 0. Релизный гейт: один ручной шаг перед всем остальным

**Supabase Dashboard → Settings → API → Exposed schemas → добавить `tasks`.**

Схема `tasks` создана и заполнена политиками, но пока её нет в списке, PostgREST её не
отдаёт: любой запрос вернёт `PGRST106` («The schema must be one of the following»), и это
будет выглядеть как «ничего не работает», а не как «забыли галочку». Ровно так же в своё
время включали `budget`.

Проверка одной строкой в консоли браузера после включения:

```js
await createClient().schema('tasks').from('list_cards').select('id').limit(1)
// { data: [], error: null }  — схема видна, списков пока нет
```

## 1. Что появляется

Второй продукт поверх пространств, после бюджета. Всё живёт внутри пространства и видно
всем его участникам:

- **Списки** — «Покупки», «Дом», «Работа». Задача без списка попадает во **«Входящие»**.
- **Задачи** со сроком, приоритетом, заметкой, исполнителем и метками.
- **Подзадачи** — ровно один уровень вложенности.
- **Исполнитель** — любой участник пространства. Закрытие задачи запоминает, кто закрыл.
- **Корзина**: удаление мягкое, восстановление в одно действие.

Чего нет и не планируется в первой версии: повторяющиеся задачи, комментарии, вложения,
несколько исполнителей, личные задачи внутри общего пространства, уведомления.

## 2. Что уже сделано в базе (не переписывать, только читать и писать)

Миграции применены 2026-09-04: `create_tasks_schema`, `tasks_triggers`,
`tasks_rls_and_grants`, `tasks_read_views`, `tasks_member_removal_hook`,
`tasks_task_labels_fk_index`, `tasks_error_hints`.

RPC-слоя здесь **нет** — в отличие от приглашений. Приглашение меняет права доступа,
поэтому оно проходит через `security definer` функции; задача — это данные внутри уже
установленной границы, и её достаточно закрыть RLS плюс поколоночными грантами. Значит
клиент пишет прямо в таблицы, как в бюджете.

### 2.1 Обращение к схеме

Схема не `public`, поэтому **каждый** запрос идёт через `.schema('tasks')`:

```ts
const supabase = createClient()
await supabase.schema('tasks').from('task_cards').select('*').eq('space_id', spaceId)
```

Забытый `.schema()` уходит в `public`, где таких таблиц нет, и возвращает `PGRST205`
(«Could not find the table»). Это самая частая ошибка первых часов работы со схемой.

### 2.2 Вью для чтения

Читаем через вью, пишем в таблицы. Все три — `security_invoker`, то есть RLS отдаёт ровно
те же строки, что и напрямую; вью меняет только форму ответа.

```
tasks.task_cards   -- задачи и подзадачи пространства, кроме удалённых
  id, space_id, list_id, list_name, parent_id, title, notes, priority,
  due_at, due_has_time, position, assignee_id, assignee_name, assignee_avatar,
  is_mine, is_done, completed_at, completed_by_name,
  created_by, created_by_name, subtask_count, subtask_done_count,
  created_at, updated_at

tasks.list_cards   -- списки пространства со счётчиками
  id, space_id, name, color, position, archived_at,
  open_count, total_count, created_at, updated_at

tasks.my_agenda    -- мои открытые задачи ПО ВСЕМ пространствам сразу
  id, space_id, space_name, list_id, list_name, parent_id,
  title, priority, due_at, due_has_time, created_at
```

Заметки, которые сэкономят время:

- `list_id` во вью **уже разрешён**: у подзадачи в таблице он всегда `null`, а вью
  подставляет список родителя. Отдельный джойн на родителя не нужен.
- `is_done` — это `completed_at is not null`, готовый булев. `completed_at` рядом, если
  надо показать «закрыто вчера».
- `assignee_name` приходит `null` только когда исполнителя нет. Если человек есть, но
  профиль почему-то не читается, вью подставит заглушку `user-xxxxxxxx` — пустоты не будет.
- `subtask_count` / `subtask_done_count` считают неудалённые подзадачи; по ним рисуется
  «3 из 5» на карточке без второго запроса.
- `list_cards.open_count` и `total_count` считают **только корневые задачи** (у подзадач
  `list_id` в таблице `null`, поэтому они в счётчик не попадают). Это то, что нужно
  показывать рядом с названием списка.
- `my_agenda` включает и подзадачи (у них есть `parent_id`), но **не содержит заголовка
  родителя**. Если он понадобится на экране — это правка вью миграцией, а не второй запрос
  из цикла.

Метки читаются прямо из таблиц: `tasks.labels` (справочник пространства) и
`tasks.task_labels` (`task_id`, `label_id`, `space_id`, `created_at`).

### 2.3 Что можно писать

Гранты выданы по колонкам. Всё, чего нет в таблице ниже, вызовет
`permission denied for table …` (`42501`), даже если строка ваша.

| Таблица | INSERT | UPDATE |
|---|---|---|
| `tasks.tasks` | `space_id, list_id, parent_id, title, notes, assignee_id, priority, due_at, due_has_time, position, completed_at` | `list_id, parent_id, title, notes, assignee_id, priority, due_at, due_has_time, position, completed_at, deleted_at` |
| `tasks.lists` | `space_id, name, color, position` | `name, color, position, archived_at` |
| `tasks.labels` | `space_id, name, color` | `name, color` |
| `tasks.task_labels` | `task_id, label_id` | — (нечего менять) |

`DELETE` разрешён на всех четырёх, но для задач он нужен только чистке корзины (§3, п. 5).

Закрыто намеренно:

- **`space_id` на UPDATE у задачи.** Перенос между пространствами — это смена границы
  доступа, а не правка поля. Понадобится — сделаем RPC.
- **`completed_by`** — ставит триггер из `auth.uid()`.
- **`created_by`, `created_at`, `updated_at`** — дефолт и триггер.
- **`task_labels.space_id`** — наследуется от задачи.
- **Всё у `anon`.** Неавторизованный запрос получает `permission denied for schema tasks`.

### 2.4 Чего база не даст сделать

| Ситуация | Что придёт | Что показать |
|---|---|---|
| подзадача к подзадаче | `23514`, `hint: subtask_depth` | «Подзадачи вкладываются только на один уровень» |
| сделать подзадачей задачу, у которой есть свои подзадачи | `23514`, `hint: has_subtasks` | «Сначала перенесите подзадачи» |
| исполнитель не участник пространства | `23514`, `hint: assignee_not_member` | «Исполнителем может быть только участник» |
| родитель не найден (или он в чужом пространстве) | `23503`, `hint: parent_not_found` | «Задача не найдена» |
| метка на несуществующую задачу | `23503`, `hint: task_not_found` | то же |
| 51-й список / 51-я метка / 10 001-я задача / 201-я подзадача | `23514`, `hint: too_many_lists` \| `too_many_labels` \| `too_many_tasks` \| `too_many_subtasks` | текст про лимит |
| список или метка с существующим именем | `23505` (`lists_space_name_idx` / `labels_space_name_idx`) | «Такой список уже есть» + открыть его |
| запись в незаданную грантом колонку | `42501` | общий отказ |
| запись в чужое пространство | `new row violates row-level security policy` | общий отказ |

**Ключ для словаря — `error.hint`, а не `error.message`.** Сообщения триггеров написаны
по-русски и меняются вместе с миграцией; `hint` — стабильный машинный ключ, добавленный
специально для клиента (`tasks_error_hints`). В английском словаре русский `message`
выглядел бы как баг.

**Отдельный случай — отказ без ошибки.** Если RLS не пропускает строку, `UPDATE` и
`DELETE` не падают: они просто не находят её и возвращают **ноль строк без `error`**. Так
же ведёт себя запись из MCP-клиента, которому не выдали право записи. Значит каждая
мутация обязана заканчиваться `.select()` и проверкой длины — точно как `rename` и `remove`
в `hooks/use-space.ts`:

```ts
const { data, error } = await supabase.schema('tasks').from('tasks')
  .update({ title }).eq('id', taskId).select('id')
if (error) return setError(refusal(error, messages))
if (!data?.length) return setError(messages.silent)   // тихий отказ
```

## 3. Восемь правил, о которые разбивается наивная реализация

**1. У подзадачи нет своего списка.** В таблице `list_id` всегда `null`; писать его
бессмысленно — триггер обнулит. Список подзадачи — это список родителя, и он приезжает
разрешённым во вью. Перенос родителя в другой список переносит подзадачи сам собой.

**2. Синхронизация только сверху вниз.** Закрытие родителя закрывает все его открытые
подзадачи — **в базе, одним триггером**. Клиент, который после «Готово» обновил только
одну строку в стейте, покажет расхождение. После закрытия задачи с подзадачами надо
перечитать её поддерево (или всю доску).

Обратного нет и не будет: закрытие последней подзадачи родителя **не** закрывает, а
переоткрытие родителя подзадачи **не** открывает. Не «чинить» это на клиенте — расхождение
видно во вью как `subtask_done_count = subtask_count` у незакрытой задачи, и это
нормальное состояние, которое стоит показать, а не спрятать.

**3. `completed_at` пишем, `completed_by` — нет.** Закрытие — это `completed_at = now()`,
переоткрытие — `completed_at = null`. Автора проставит триггер. Значение времени
нормализуется на сервере (будущим числом задачу не закрыть), поэтому оптимистичный UI
должен брать итог из `.select()`, а не из того, что отправил.

**4. Удаление мягкое.** Обычное «Удалить» — это `deleted_at = now()`; вью его сразу
прячет. Мягкое удаление родителя уносит подзадачи, восстановление возвращает **только тех,
кто ушёл вместе с ним**. Настоящий `DELETE` остаётся для «Очистить корзину» — он уносит
подзадачи каскадом и необратим.

**5. Позиции дробные.** `position` — `numeric`, вставка между двумя соседями = среднее
арифметическое их позиций, соседей двигать не нужно. Не передавать `position` при создании
вообще — триггер поставит `max + 1024` в конец нужной группы (группа — это пространство +
список + родитель).

**6. Исполнитель обязан быть участником.** Список кандидатов — `public.space_people` того
же пространства (`user_id`, `display_name`, `avatar_url`, `is_me`). Свободного ввода нет.
Когда участника исключают или он выходит, база **сама снимает его с открытых задач**;
закрытые задачи исполнителя сохраняют как исторический факт. Экран, открытый в этот момент,
об этом не знает — после любого изменения состава пространства перечитывайте задачи.

**7. Срок — это дата или дата со временем.** `due_at` хранит момент, `due_has_time`
говорит, показывать ли время. «До пятницы» — это `due_has_time = false`, и рисовать у неё
«00:00» неправильно. Выставить флаг без даты база не даст.

**8. Пространство у задачи не меняется.** Переноса между пространствами нет ни в UI, ни в
API. Если человек просит — это «скопировать текст и создать заново».

## 4. Экраны

Задачи — отдельный раздел верхнего уровня, рядом с дашбордом, а не вкладка настроек.
В `components/site-header.tsx` добавляется пункт `nav.tasks`.

### 4.1 `/[lang]/tasks` — «Мои задачи»

Первый экран продукта и точка входа из меню. Источник — `tasks.my_agenda`, один запрос на
все пространства.

```
Мои задачи
  ПРОСРОЧЕНО (2)
    ● Оплатить страховку        вчера        Семейный · Дом
    ● Забрать посылку           2 дня назад  Личное
  СЕГОДНЯ (1)
    ● Купить молоко             18:00        Семейный · Покупки
  ДАЛЬШЕ (4)
    ...
  БЕЗ СРОКА (7)
```

- Группы считает клиент: `due_at < now()` — просрочено, `due_at` внутри сегодняшних суток
  **в поясе браузера** — сегодня. В базе ничего подобного не хранится (§5, п. 4).
- Строка справа — `space_name · list_name`; `list_name` пустой для «Входящих».
- Клик по строке открывает карточку задачи (§4.3) поверх текущего экрана.
- Пустое состояние — `components/ui/empty.tsx`, как на дашборде.

### 4.2 `/[lang]/tasks/[spaceId]` — доска пространства

Выбор пространства — тем же компонентом, что на дашборде (`components/dashboard/space-filter.tsx`),
или ссылками из `my_spaces`.

```
Семейный бюджет                                   [+ Список]
┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ Входящие    3  │ │ Покупки     5  │ │ Дом         0  │
│ ○ Позвонить …  │ │ ○ Купить мол…  │ │ пусто          │
│ ○ Записаться…  │ │   ▸ 1 из 2     │ │                │
│ ✓ Оплатить …   │ │ ○ Хлеб      К. │ │                │
│ [+ Задача]     │ │ [+ Задача]     │ │ [+ Задача]     │
└────────────────┘ └────────────────┘ └────────────────┘
                                        Корзина (2) ▾
```

- Колонки: «Входящие» (виртуальная, `list_id is null`) плюс `list_cards`, отсортированные
  по `position`, архивные скрыты.
- В колонке — **только корневые задачи**: `task_cards` с `parent_id is null`. Подзадачи
  видны в карточке и свёрнутым счётчиком «1 из 2» под родителем.
- Закрытые задачи по умолчанию свёрнуты в «Показать закрытые (N)» — иначе список
  захламляется через неделю.
- Быстрое добавление: поле «+ Задача» в конце колонки, `Enter` создаёт и оставляет фокус
  для следующей.
- Перетаскивание задач между колонками и внутри колонки меняет `list_id` и `position`
  одним `UPDATE`.
- «Корзина» — раскрывающийся блок внизу: `tasks.tasks` (таблица, не вью) с
  `deleted_at is not null`, кнопки «Восстановить» и «Очистить».

### 4.3 Карточка задачи

Диалог поверх доски (`components/ui/alert-dialog.tsx` уже есть; для формы удобнее обычный
`Dialog` — добавить через `shadcn`).

```
[✓] Купить молоко
    Список: Покупки ▾        Исполнитель: Ксения ▾
    Срок: 5 сентября, 18:00 ▾   Приоритет: Обычный ▾
    Заметка: ...
    Метки: [дом] [+]
    Подзадачи
```

- «Исполнитель» — выпадающий список участников из `space_people` плюс «Без исполнителя».
- «Список» — из `list_cards` плюс «Входящие». У подзадачи поле скрыто (правило 1).

### 4.4 Настройки списков и меток

Внутри доски, отдельного экрана настроек не нужно: переименование по двойному клику,
цвет — палитрой, «Архивировать» и «Удалить» — в меню колонки.

**Удаление списка не удаляет задачи** — они возвращаются во «Входящие». Диалог должен так
и говорить: «Список удалится, 5 задач переедут во „Входящие“». Это важное отличие от
привычного поведения других приложений, и молчать о нём нельзя.

## 5. Особенности реализации, которые надо учесть

**1. `numeric` приезжает строкой.** `position` — та же история, что `amount` в бюджете
(см. комментарий в `lib/budget/dashboard.ts`): типизировать как `string | number` и
прогонять через `Number()`. Сортировка по нему на клиенте без приведения даст
лексикографический порядок, где `1024` окажется раньше `512`.

**2. Потолок в 1000 строк.** PostgREST отдаёт максимум 1000 строк за запрос независимо от
`.limit()`. Для доски это далеко, но корзина и «показать закрытые» за год упрутся. Там же,
где это возможно, — постранично через `.range()`, как `PAGE_SIZE` в бюджете.

**3. `statement_timeout` у роли `authenticated` — 8 секунд.** Массовые операции («закрыть
все», «очистить корзину») резать на пачки: одним `in.(…)` не больше полусотни
идентификаторов.

**4. Часовой пояс считает клиент.** `due_at` хранится в UTC. «Сегодня» — это диапазон
`[начало суток, конец суток]` в поясе браузера, переведённый в ISO; фильтр
`.gte('due_at', from).lt('due_at', to)`. В базе нет ни пояса пользователя, ни поля
«просрочено» — и то и другое считается на чтении. (Для ассистента это открытый вопрос: у
него пояса нет вовсе, см. `plan-tasks.md` §14.)

**5. Стабильная сортировка.** `order('position')` плюс `order('created_at')` вторым ключом:
позиции не уникальны, и без второго ключа две задачи с одинаковым `position` будут
меняться местами между запросами.

**6. Дробные позиции деградируют.** Постоянная вставка «между двумя» удлиняет дробь.
Практический порог — когда строка позиции длиннее 30 символов: тогда клиент перенумеровывает
колонку (`1024, 2048, 3072…`) одним пакетом. Это дешевле, чем фоновая задача, которой всё
равно негде выполняться: `pg_cron` в проекте не установлен.

**7. Оптимистичный UI — только для чекбокса и перетаскивания.** Всё остальное (создание,
смена исполнителя, перенос в список) слишком легко откатывается в неправильное состояние
из-за триггеров. Для создания задачи достаточно спиннера на кнопке.

**8. Двойной клик по «Готово» безопасен, но кнопку всё равно блокируем.** Повторное
закрытие идемпотентно (второй `UPDATE` попадает в ветку «вне переходов» и ничего не меняет),
однако без `busy` пользователь успевает кликнуть «Готово» и «Отменить» в неопределённом
порядке. Состояние `busy` — тем же типом-объединением, что в `hooks/use-space.ts`
(`{ kind: 'complete'; taskId: string }`).

**9. Перечитывание после мутаций.** Паттерн `reloadToken` из `use-space.ts`: счётчик в
зависимостях эффекта. Точки, где перечитать обязательно: закрытие/переоткрытие задачи с
подзадачами, мягкое удаление и восстановление, изменение состава пространства.

**10. Realtime для задач не включён.** Публикация `supabase_realtime` содержит только
`space_invites`. Пока экран обновляется по действиям пользователя; если понадобится «вижу,
как жена вычёркивает пункты» — это одна миграция
(`alter publication supabase_realtime add table tasks.tasks`) плюс подписка с фильтром
`space_id=eq.<id>`. RLS Realtime проверяет от лица подписчика, так что фильтр — ради
трафика, а не безопасности.

**11. Имена списков и меток не переводятся.** Это данные пользователя. Переводится только
слово «Входящие» — потому что в базе такого списка нет вовсе, это `list_id is null`.

**12. Поиск по задачам — без индекса.** Ни `pg_trgm`, ни полнотекстового индекса на
`title` нет. `ilike` по одному пространству с `limit` — приемлемо; глобальный поиск по всем
пространствам в первой версии не делаем.

**13. Изоляция в MCP.** Инструменты ассистента (`lib/mcp/tools.ts`) принимают и возвращают
**имена**, а не идентификаторы: `assignee: "Ксения" | "me" | null`, резолв через
`space_people` внутри инструмента. `tests/mcp-isolation.test.mts` требует, чтобы в ответе
пользователя A не встречалось ни одного идентификатора B, и новые read-инструменты надо в
него добавить.

**14. Текст задачи — недоверенный ввод для ассистента.** Заголовок и заметку пишет другой
участник пространства, а читает их модель, у которой есть инструменты записи. Ответы
инструментов должны обрамлять пользовательский текст и явно помечать его как данные — так
же, как это делает Supabase MCP со своими ответами.

## 6. Хуки и файлы

Ничего принципиально нового по форме — повторяем то, что уже работает.

```
hooks/use-agenda.ts        мои задачи по всем пространствам (my_agenda)
hooks/use-task-board.ts    списки + задачи одного пространства (list_cards + task_cards)
hooks/use-task.ts          одна задача с подзадачами и метками, для карточки
lib/tasks/format.ts        группировка по срокам, «просрочено», формат даты с due_has_time
components/tasks/*.tsx     board, column, task-row, task-dialog, trash
app/[lang]/tasks/page.tsx
app/[lang]/tasks/[spaceId]/page.tsx
```

Форма хука — как `use-space.ts`: загрузка внутри `useEffect` с флагом `active`,
`reloadToken` для перезапроса, `busy` объединением, все строки приходят параметром
`messages` (хук не хранит текстов), состояние ошибки — одна строка.

`lib/supabase/errors.ts` дополняется одной функцией:

```ts
/**
 * Схема tasks не имеет RPC-слоя, поэтому ожидаемые исходы приходят исключениями
 * триггеров. Разбирать их message нельзя: он по-русски и меняется вместе с
 * миграцией. Стабилен hint — машинный ключ, который триггеры проставляют
 * специально для клиента.
 */
export function taskRefusal(
  error: PostgrestError,
  messages: Record<string, string> & { notAllowed: string; unknown: string }
): string {
  if (error.code === '42501') return messages.notAllowed
  if (error.hint && messages[error.hint]) return messages[error.hint]
  if (error.code === '23505') return messages.duplicateName
  return messages.unknown
}
```

## 7. MCP-инструменты (отдельная задача, контракт здесь)

Из ассистента разрешено всё, включая удаление, — но `delete_task` ставит `deleted_at`, а не
удаляет строку. Худшее, что сделает prompt injection, — спрячет задачи в корзину, откуда они
возвращаются одним действием.

```
list_task_lists(space?)                     list_cards
list_tasks(space?, list?, filter, assignee?) task_cards; filter: open|today|overdue|done|all
my_tasks()                                   my_agenda
create_list(space, name, color?)             идемпотентен по имени (ловит 23505)
create_task(space, title, list?, due?, priority?, assignee?, notes?, parent?)
update_task(id, …)
complete_task(id) / reopen_task(id)
delete_task(id) / restore_task(id)          мягко
add_label(task, label) / remove_label(task, label)
```

Ограничений «только из приложения», как у приглашений, нет: задача не меняет права доступа.
Ограничение на массовость — не больше 50 идентификаторов за вызов.

## 9. Чего не делать

- **Не писать `completed_by`, `created_by`, `space_id` у задачи и `space_id` у метки.**
  Гранта нет, ответ будет `42501`, а значения и так проставятся сами.
- **Не звать `.delete()` для обычного удаления задачи.** Только `deleted_at`; настоящий
  `DELETE` — исключительно в «Очистить корзину».
- **Не разбирать `error.message`.** Только `error.hint` и `error.code`.
- **Не повторять серверные правила «на всякий случай».** Проверять на клиенте глубину
  вложенности, членство исполнителя или лимиты — значит завести вторую реализацию, которая
  рано или поздно разойдётся с первой. Клиент **прячет** недоступные действия (не
  показывает «+ подзадача» у подзадачи) и **показывает** отказ, когда он всё же пришёл.
- **Не строить локальную истину о подзадачах.** Их закрывает база.
- **Не заводить настоящий список «Входящие».** Это `list_id is null` и слово в словаре.
- **Не обходить `my_agenda` циклом по пространствам.** Она для того и сделана.
- **Не добавлять `assignee_id` в ответы MCP-инструментов.** Только имена.
